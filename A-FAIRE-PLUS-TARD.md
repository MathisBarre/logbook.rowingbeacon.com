# À faire plus tard

Liste vivante de ce qui est décidé ou repéré mais hors du périmètre en cours. Ajouter une ligne dès qu'un sujet est identifié, la retirer quand il est livré.

## Feuille de route v2 (après la migration SQLite et le modèle efa2)

- **Refonte des droits** : le système actuel de niveaux (catégorie d'âge, type de pratiquant, seuils d'alerte et de blocage par type de bateau) est jugé trop complexe. Le repenser avec les groupes d'efa2 en un seul système plus simple, puis livrer le module « Groupes et droits ». Les tables de groupes existent déjà pour l'import efa2.
- **Plusieurs administrateurs** et changement du mot de passe.
- **Plusieurs cahiers par saison**, avec bascule automatique.
- **Messages et notifications** (message au responsable, alertes).
- **Recherche dans le cahier**, assistant de correction et fusion de doublons dans l'interface.
- **Saisie rapide** : équipages types, valeurs par défaut par bateau ou par rameur.
- **Alertes de sécurité au départ** (nuit, météo).
- **Historique des modifications lisible par fiche**, à afficher dans l'interface (la table est alimentée dès la v2).
- **Anonymisation RGPD** d'une fiche de rameur depuis l'interface (ADR 0001). La fonction `anonymizeRower` est prête : elle efface les données personnelles, archive la fiche et purge son journal des modifications ; il reste le bouton et sa confirmation, puis recharger les données en mémoire (sinon la liste des réservations garde l'ancien nom, contact et motif, et les réécrit en base à la première modification).

## Suites des modules livrés en v2

- **Mises à jour** (ADR 0006) : build macOS (aucun aujourd'hui, donc pas de mise à jour Mac) ; installation sans intervention la nuit, quand aucune sortie n'est en cours ; une AppImage Linux dans un dossier en lecture seule ne peut pas se remplacer (prévenir et proposer le téléchargement) ; vérifier dans l'app compilée le passage complet 2.0.x → version suivante sous Windows et Linux, impossible dans l'environnement de revue. Chaîne de release : épingler les actions GitHub du workflow miroir par SHA ; signer les installeurs dans une étape séparée après le build, pour que les scripts de build des dépendances ne voient pas la clé de mise à jour ; certificat de signature Windows (Authenticode ou Azure Trusted Signing) pour supprimer l'alerte SmartScreen ; republier un MSI quand l'updater sera monté à une version qui distingue MSI et NSIS (2.0.x n'a qu'une entrée Windows).
- **Import efa2** : fusionner un projet efa2 dans une base qui a déjà des données (aujourd'hui l'import remplace tout) ; importer les données efa 1.x ; exporter aussi `cfg/types.efa2types` pour que les types de sortie propres au club ne redeviennent pas « NORMAL » dans un efa neuf ; les noms libres importés reviennent comme fiches archivées à l'export ; versionner la fiche bateau quand son gréement change dans RB (aujourd'hui les sorties créées dans RB sur un ancien gréement perdent leur variante efa) ; garder d'un export à l'autre le numéro efa des sorties créées dans RB (il est recalculé à chaque export) ; écrire le ZIP exporté sous un nom provisoire puis le renommer (la portée de « Enregistrer sous » ne couvre que le fichier choisi).
- **Sauvegardes** : restauration sélective (une partie des données seulement) ; envoi d'une sauvegarde par e-mail ; vérifier dans l'app compilée que le dossier de copie externe reste élagué après un redémarrage (plugin persisted-scope ajouté, non compilable dans l'environnement de revue) ; choisir dans une liste quand un dossier contient plusieurs projets efa (aujourd'hui on tape le nom).
- **Données efa gardées sans écran** (table `efa_record`) : avaries d'un bateau inconnu, messages, équipages types, plans d'eau, groupes de sorties, travail bénévole, insignes, règles d'accès des bateaux (groupes autorisés, groupe obligatoire, chef de bord obligatoire), interdiction de bateau par personne, statuts attribués selon l'âge. À reprendre par les modules correspondants et par la refonte des droits.

- **Types de sortie** : écran pour ajouter, renommer ou masquer des types (la table `outing_type` accepte déjà des libellés libres) ; regrouper les étapes d'une randonnée ou d'un stage comme efa2.
- **Réservations** : annuler une seule occurrence d'une réservation hebdomadaire ; option pour réserver le droit de modifier ou supprimer aux administrateurs ou au titulaire ; réservations sans heure (journée entière) d'efa, gardées aujourd'hui sans écran ; suggestion contextuelle du module (clé `modules.reservations.suggestion` prête) ; purge des réservations passées ; vérifier dans efa qu'un `WEEKLY_LIMITED` aux bornes lointaines (01.01.1970 / 31.12.2999, réservation hebdomadaire bornée d'un seul côté) est accepté ; le champ heure suit l'horloge du système, pas le réglage 12 h / 24 h ; créneau hebdomadaire qui finit à minuit (00:00) ou passe minuit, refusé aujourd'hui (saisir 23:59) ; ajouter « réservation » au `GLOSSARY.md` ; garder un plus haut numéro efa de réservation (aujourd'hui, supprimer la dernière réservation exportée puis en créer une redonne le même numéro) ; le titre du dialogue de réservation repasse à « Nouvelle réservation » pendant l'animation de fermeture ; un créneau hebdomadaire qui tombe dans l'heure sautée au passage à l'heure d'été (dimanche 02:00-03:00) ne s'affiche pas ce jour-là.
- **Fusion de bateaux ou de rameurs** (quand elle aura un écran) : déplacer aussi leurs réservations, sinon l'export efa écrit une réservation sur un bateau absent, et une réservation d'un rameur fusionné s'affiche sans titulaire.
- **Chef de bord** : rendre le chef de bord obligatoire bateau par bateau (aujourd'hui l'option vaut pour tout le club).
- **Invités** : fusionner une fiche invité avec un membre existant depuis l'interface, en redirigeant ses sorties (ADR 0001) ; aujourd'hui on peut seulement passer l'invité en membre.
- **Distances** : départ / arrivée, aller-retour, écluses et plans d'eau des destinations efa2 (les plans d'eau ne sont pas modélisés) ; km par rameur et par bateau dans les fiches Rameurs et Bateaux de Gestion (les rapports de Statistiques les donnent déjà).
- **Avaries** : mémoriser le numéro efa attribué à une avarie créée dans RB (recalculé à chaque export dans l'ordre de saisie : stable tant qu'aucune avarie n'est supprimée) ; relier à la sortie une avarie importée d'efa (`LogbookText` « #N », aujourd'hui perdu à l'aller-retour) ; afficher le nombre d'avaries exportées dans le bilan d'export ; modifier les détails d'une réparation (note, coût, réparateur) sans rouvrir l'avarie ; afficher une devise pour le coût de réparation ; l'anonymisation RGPD d'un membre efface son nom des avaries mais pas encore du texte des incidents ; au retour, la sortie, l'incident et l'avarie s'écrivent séparément (si l'avarie échoue, le message « hors service » s'est déjà affiché) ; dans la fiche bateau, réparer une avarie bloquante depuis la fiche remet la case « hors service » à l'état des avaries, même cochée à la main juste avant ; un bateau archivé encore indisponible sort « HIDE » à l'export efa et perd son indisponibilité au réimport ; sur tablette, le détail d'une avarie non bloquante n'apparaît qu'au survol de l'indicateur ; le message « avarie déclarée » s'affiche avant la fin de l'écriture (comme ailleurs dans l'app) ; la saisie a posteriori d'une sortie (PR #8) devra décider si une avarie déclarée après l'heure de la sortie bloque l'enregistrement ; afficher le déclarant en nom libre venu d'efa (gardé seulement dans `efa_record`) ; déclarer une avarie au retour sans cocher d'incident ; indicateur d'avarie aussi en mode édition admin du ponton ; supprimer la colonne `boat.is_in_maintenance`, plus écrite depuis la v2.1 ; vérifier l'aller-retour des avaries avec un vrai efa 2.5.3 ; corriger la date de déclaration d'une avarie (une date efa erronée dans le futur reste affichée, la réparation est seulement permise dès maintenant).
- **Fiche membre** : proposer la catégorie d'âge à partir de la date de naissance ; chercher un rameur par n° de licence.

- **Saisie a posteriori et correction des sorties** (livrées) : déclarer un incident en saisissant une sortie déjà faite ; contrôle des niveaux de rameurs non appliqué aux sorties saisies après coup ni aux corrections (la sortie a déjà eu lieu), à revoir avec la refonte des droits ; limiter l'équipage à 24 rameurs dans l'éditeur (l'export efa coupe au-delà) ; pouvoir vider une distance ; ouvrir l'éditeur depuis la fenêtre de fin de sortie efface ce qui y était déjà saisi ; à l'anonymisation, purger aussi les anciens commentaires de sortie gardés dans `change_log` ; un invité tapé dans l'éditeur reste en base si l'enregistrement échoue ensuite ; un parcours supprimé depuis s'affiche « Aucun parcours » mais reste enregistré ; accessibilité de l'éditeur (focus sur l'alerte d'avertissements, `fieldset` pour la question encadrement, erreurs reliées aux champs) ; tester les écrans dans l'app Tauri compilée ; vérifier que l'alerte « Enregistrer quand même » couvre bien l'éditeur quand il défile ; ne réafficher l'alerte de chevauchement que si les heures, le bateau ou l'équipage changent (une sortie importée qui chevauchait déjà la redemande à chaque correction) ; le cas d'usage ne vérifie pas que la configuration appartient au bateau choisi (le formulaire la remet à zéro) ; export efa : une sortie efa sur un bateau connu seulement par son nom garde l'ancienne variante si on la passe sur un bateau sans configuration, et un cahier à dates personnalisées nommé comme une année peut garder une sortie déplacée hors de ses dates ; ## Statistiques

- Autres fournisseurs d'IA avec leur API propre (Gemini, Mistral natif) ; aujourd'hui Mistral et les modèles locaux passent par « Compatible OpenAI ».
- Prix des serveurs compatibles (ligne de coût) : aujourd'hui aucun coût n'est estimé pour eux.
- Réponses de l'IA en flux continu (streaming).
- Plusieurs tableaux de bord (la table le permet déjà, `dashboard_id`).
- Installation automatique dans Claude Desktop (fichier MCPB) et serveur MCP HTTP.
- Rapports programmés ou envoyés par e-mail (demande de CA Nantes).
- Statistiques des réservations et des groupes de rameurs : `boat_reservation` est hors du dictionnaire (donc refusée à l'Explorateur, à l'IA et au MCP) tant que ses colonnes titulaire, contact et motif ne sont pas classées.
- Glisser-déposer sur le tableau de bord.
- Insignes et compétitions DRV / LRV.
- Saison commune aux fiches Rameurs et Bateaux de Gestion et à leurs comparaisons (aujourd'hui : même mois de début, mais fin au 31 juillet 00:00).
- Chiffrement de la clé API avec le mot de passe responsable, quand le mot de passe sera salé.
- Statistiques de performance (vitesse, temps sur un parcours) : il faudrait des temps fiables.
- Date d'adhésion réelle des membres (aujourd'hui la fidélisation se calcule depuis la première sortie).
- Le mode de sortie retenu pour un serveur compatible (`json_schema`, `json_object` ou texte libre) est mémorisé par adresse et par modèle jusqu'au redémarrage seulement : chaque lancement refait au plus deux essais refusés.
- Les modèles locaux suivent mal un schéma de réponse long : l'application valide la réponse et la fait corriger, mais un petit modèle (moins de 8 milliards de paramètres) échouera souvent.
- Le contexte envoyé à l'IA fait 40 000 à 50 000 caractères avec le dictionnaire complet (environ 12 000 jetons, mis en cache) : raccourcir les descriptions du dictionnaire pour viser 15 000 à 25 000.
- Le prix de lecture du cache de Haiku 5.5 est supposé (10 % du prix d'entrée) : la ligne de coût est une estimation, à vérifier sur une facture réelle.
- L'application n'a pas de thème sombre : les graphiques en ont un, prêt, choisi par la classe `dark` de `<html>`.
- Les largeurs de texte des graphiques sont estimées sans mesurer le DOM : une police inhabituelle ou un fort zoom peut faire se chevaucher des libellés.
- Mesurer sur un Raspberry Pi 4 l'effet de `temp_store=MEMORY` et des déclencheurs désactivés sur les connexions de statistiques, et la durée des rapports lourds sur dix ans d'historique (8 à 12 s estimées, délai maximal 20 s).
- Fusion des fiches : `v_rowers` et `v_boats` écartent les fiches fusionnées (`merged_into_id`), mais `v_outings` et `v_outing_rowers` gardent l'ancien identifiant et l'ancien nom, si bien qu'un rameur ou un bateau fusionné compterait deux fois dans les rapports par rameur ou par bateau. Aucun écran n'écrit `merged_into_id` aujourd'hui : quand la fusion arrivera, soit elle réaffecte les sorties à la fiche gardée, soit les vues passent par `merged_into_id` (en mesurant l'effet sur les rapports lourds).
- Mesurer sur un Raspberry Pi 4 le plafond mémoire d'une requête de statistiques (256 Mo, `MEMORY_BUDGET_BYTES` ; le rapport le plus gourmand en prend 43 Mo sur six saisons) et le temps de réponse de l'IA avec 16 000 jetons de sortie (délai de 10 minutes sans streaming).
- Profils de performances : vérifier la détection de la mémoire sous macOS (`sysctl hw.memsize`) et Windows (`GlobalMemoryStatusEx`) sur des versions compilées (seul Linux est testé ici ; la compilation Windows est vérifiée en croisé), mesurer sur un Raspberry Pi 5 de 8 Go si Standard lui conviendrait, et vérifier le délai d'attente des clients MCP (Puissant donne 50 s à `run_report`, sous la minute supposée de Claude Desktop).
- Hors Unix (Windows), le cache des résultats ne repère une base remplacée sous le même chemin que par `PRAGMA data_version` (pas d'identité de fichier) ; les restaurations passent par SQL, ce qui suffit aujourd'hui.
- Une base en WAL dans un dossier en lecture seule sans son fichier `-shm` est illisible par SQLite : le moteur l'explique dans son message d'erreur, sans solution automatique.
- Si quelqu'un ajoute une expression `plugins.shell.open` dans la configuration Tauri, elle doit aussi accepter `.*rowing-beacon-[a-z0-9-]+\.html` (ouverture du rapport annuel exporté).
- Serveur MCP sous Windows : `Rowing Beacon.exe --mcp` est une application fenêtrée (sous-système GUI) ; elle hérite des tubes de Claude Desktop et doit fonctionner, mais ce n'est pas encore vérifié sur une version compilée. Si Claude Desktop n'obtient pas de réponse, livrer le binaire console `rb-mcp` déjà prêt dans `crates/rb-analytics` : `cargo build --release -p rb-analytics --bin rb-mcp`, le copier en `src-tauri/binaries/rb-mcp-x86_64-pc-windows-msvc.exe`, ajouter `"externalBin": ["binaries/rb-mcp"]` sous `bundle` dans `tauri.conf.json`, et faire pointer `paths::mcp_info().exePath` vers `rb-mcp.exe` à côté de l'exécutable sous Windows.

## Dette et défauts repérés

- Le mot de passe admin est haché en SHA-256 sans sel ; passer à une dérivation salée (argon2 ou PBKDF2) lors du chantier des administrateurs.
- L'import / export efa2 et les sauvegardes sont testés sur la base (Node) et validés par efa lui-même, mais pas encore dans l'application Tauri compilée (sélecteurs de fichiers, « Enregistrer sous » de l'export, portée fs, rechargement après restauration ou après un import échoué, raccourci Ctrl+Z).
- Le store « admin edit mode » et `EditBoatRow` ne sont jamais déclenchés : code mort à supprimer ou à brancher.
- Supprimer une sortie laisse son incident orphelin.
- Plusieurs textes restent en français en dur malgré l'i18n (libellé « Autre » des types de bateau, messages Zod). Voir `I18N_IMPLEMENTATION.md`.
- La dépendance `xlsx` est téléchargée depuis `cdn.sheetjs.com`, hors du registre npm : une installation échoue si ce domaine est bloqué.
- Les catégories d'âge (J10 à Senior) sont figées et propres à la France.
- Pas de build macOS documenté.
- `drizzle-gen/` et `schema.ts` ne décrivent que les sorties ; les migrations SQL écrites à la main font foi. Régénérer ou retirer `drizzle-gen/`.
- Les anciennes tables `session` et `session_rowers` restent en base après la migration v2 (copiées dans `outing`) ; les supprimer dans une version ultérieure, une fois la migration éprouvée chez les clubs.
- L'import / export JSON maison (`importExport.ts`) ne reprend pas les armements ni les fiches membres complètes.
- Avertissements React en console : `Button` ne transmet pas sa `ref` (utilisé avec `DialogTrigger asChild`) et le formulaire d'onboarding passe d'un champ non contrôlé à contrôlé.
- Écritures non atomiques : le plugin SQL de Tauri passe par un pool de connexions, une transaction ne peut donc pas couvrir plusieurs appels. Si `saveBoat` (bateau puis armements) ou « Supprimer les données » échoue au milieu, la base peut garder une partie de l'écriture ; l'écran est rechargé depuis la base. À traiter par une commande Rust transactionnelle.
- Aucun test de bout en bout : un banc d'essai navigateur (IPC Tauri simulé avec sql.js + Playwright) a servi pendant le développement de la v2 ; l'ajouter au dépôt permettrait de tester les parcours en CI.
- Une date de départ saisie très loin dans le futur (année erronée) est acceptée ; le retour est ensuite refusé tant que l'heure de fin ne la dépasse pas. Borner le départ (par exemple 24 h au plus dans le futur). Déjà le cas avant la v2.
- Renommer un rameur, un bateau ou un parcours pendant une sortie laisse l'ancien nom affiché sur le ponton jusqu'au redémarrage (copie des noms dans le store des sorties en cours) ; résoudre les noms par id à l'affichage. Déjà le cas avant la v2.
- L'import JSON maison compare les noms de rameurs à toutes les fiches, invités et archivés compris, et en tenant compte des accents : un membre homonyme d'un invité est ignoré sans message.
- Sans le module Fiche membre, modifier le nom d'un rameur redécoupe prénom et nom au premier espace (« Jean Pierre » / « Dupont » devient « Jean » / « Pierre Dupont »).
- Au départ, un nom tapé qui correspond à un membre archivé crée un nouvel invité (la recherche ne porte que sur les membres actifs) ; proposer plutôt de réactiver le membre.
- Une écriture qui échoue de façon passagère (base verrouillée) peut être réappliquée par l'écriture suivante de la même fiche, faite avant le rechargement : chaque écriture réécrit la fiche entière. N'écrire que les champs modifiés, ou bloquer les modifications tant qu'un rechargement est en attente.
- Les saisons finissent le 31 juillet à 00:00 (`getSeasonDate`) : les sorties du 31 juillet ne comptent dans aucune saison. Déjà le cas avant la v2. Les rapports de Statistiques utilisent des bornes exclusives et ne sont pas concernés.
- La durée d'une sortie de plusieurs jours compte les nuits (fin moins début) dans les statistiques. Les rapports de Statistiques excluent ces sorties des heures sur l'eau.
- Les sorties migrées de la v1 ont tous leurs équipiers en rôle « rameur », barreur compris (la v1 ne notait pas qui barrait) : temps de barreur et nombre de colonnes rameurs de l'export sont faussés pour l'historique d'avant la v2. Le dire dans le message de fin de migration.
- Le cahier n'affiche pas l'armement de la sortie (il est enregistré et exporté).
- Les messages de succès des paramètres (bateau, rameur, parcours) s'affichent avant le résultat de l'écriture ; en cas d'échec on voit le succès puis l'erreur.
- Un invité créé ou réactivé au départ reste en base si l'enregistrement de la sortie échoue ensuite (fiche archivée seulement, sans sortie).
- Le message de fin de migration v1 ne s'affiche qu'une fois : le réafficher tant qu'il n'a pas été lu (Router).
- La modification groupée de rameurs (`BulkUpdateRower`) n'a pas de valeurs par défaut. Déjà le cas avant la v2.
- `StopSession.execute` n'est pas idempotent : deux appels terminent deux fois la sortie. Le formulaire bloque le double clic ; ajouter la garde dans le cas d'usage.
- Les comparatifs rameurs affichent le nombre de sorties comme barreur mais pas leur durée (visible seulement dans la fiche du rameur).
- Bornes de saison des stats bateaux / rameurs : la date locale des sorties est comparée à une borne en UTC (`toISOString`), une sortie tardive du 30 juillet tombe hors saison.
- Une distance de 0 km est acceptée et affichée « 0 km » au lieu de « pas de distance ».
- Paramètres > Rameurs : après l'archivage du dernier invité, la vue invités se rouvre seule au prochain invité créé.
- Migration v1 : le message « éléments illisibles » compte aussi les simples notes (doublon exact entre table et localStorage, valeur abandonnée sur une ligne gardée) ; séparer les deux. Les rameurs d'une sortie de table ignorée mais reprise depuis le localStorage ne sont pas notés.
- Import efa2, fichiers abîmés : une date impossible (« 32.13.2025 ») sur une sortie dont l'heure de fin précède le départ bloque tout l'import (valider les dates pour classer l'entrée comme illisible) ; une variante répétée dans `TypeVariant` (« 1;1 ») fait échouer l'import (dédoublonner) ; une référence `&#0;` donne un caractère NUL qui casse le script SQL ; un fichier de données vide ou tronqué fait refuser tout le projet avec « pas un projet efa » sans essayer la copie `.s0` d'efa ; un nom de fichier à accent décomposé (macOS HFS+) n'est pas reconnu (comparer en NFC).
